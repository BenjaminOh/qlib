- **[2026-08-26] 16:00 `reconcile_balance` — 잔고 차이로 원장을 맞춘다.** 09:20 `reconcile_fills`
  와 다른 일이다: 그쪽은 아침 주문의 **체결가를 확정**하고, 이쪽은 **원장이 모르는 매도를

  ① **09:25 사다리 예약의 체결** — `reconcile_fills` 는 09:20 에 돌아 예약보다 먼저 지나가고,
  Pass 2 는 `o.price is None` 인 주문만 보는데 사다리는 지정가라 대상 밖이며, 다음 날
  정산기는 `trade_date == today` 라 어제 예약을 안 본다.
  ② **사용자의 MTS 직접 매도** — `/live/orders` 는 로컬 `orders` 테이블만 읽고 KIS 를 한 번도
  부르지 않으며, `reconcile_fills` 도 방향이 DB → KIS 라 우리 주문번호로 조회해 없으면 넘어간다.
  전량을 팔면 KIS 잔고에서도 사라져 **전 화면에서 흔적 없이 증발했다.**

  판정 규칙: `원장 순수량 − KIS 보유수량 = 우리가 모르는 매도량` → **① 우리 미체결 매도에
  먼저 배분**(안 하면 사다리 체결을 "사용자가 팔았다"로 오인) → ② 남으면 합성 SELL.
  `gap < 0`(수동 **매수**)은 기록하지 않는다 — 합성 BUY 를 쓰면 사다리·트레일이 사용자가
  직접 산 종목을 팔러 간다. 차이 기반이라 **멱등**이다.

  **되돌리기** — 합성 행은 `kis_order_id IS NULL AND status='FILLED'` 로 유일하게 식별된다
  (우리가 낸 주문은 반드시 주문번호를 갖고, 시뮬 행은 `SIMULATED` 다):
  ```sql
  DELETE FROM fills WHERE order_id IN (
      SELECT id FROM orders WHERE kis_order_id IS NULL AND status='FILLED');
  DELETE FROM orders WHERE kis_order_id IS NULL AND status='FILLED';
  ```
  안전장치: 잔고 조회 실패 시 아무것도 쓰지 않는다(**빈 잔고를 "전량 매도"로 읽으면 원장
  전체가 날아간다**). 불일치가 `live_manual_exit_max_per_day`(5)를 넘으면 쓰지 않고 알림만.
  봉합 가격은 체결내역 → 우리 지정가 → 그날 종가 순으로 물러나고 `reasons.exit.price_source`
  에 남는다. 화면에서는 "수동" 배지 + "종가 추정" 라벨로 구분된다.
