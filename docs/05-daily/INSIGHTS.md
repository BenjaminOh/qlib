# INSIGHTS — 일일 점검 에이전트 누적 학습

> **이 파일의 목적**: 매일 16:40 점검 에이전트가 세션을 시작할 때 **가장 먼저 읽는 지식 베이스.**
> 일일 보고서(`YYYY-MM-DD.daily.md`)는 그날의 사실 기록, 이 파일은 날짜를 관통하는 **지속 지식**만 담는다.
> 갱신 규칙: 새 교훈은 날짜와 함께 추가, 반증된 항목은 삭제하지 말고 ~~취소선~~+반증 근거 기록.

  (**누적 6회**, 최근 8/4 16:50) — push 후 5~8분 내 Jenkins 빌드 생성 확인, 미반응이면 빈 커밋

- **[2026-08-17] beat는 한국 공휴일을 모른다 — 휴장일 가드 도입.** `day_of_week="mon-fri"`라
  광복절 대체공휴일에도 전 태스크가 발화, 09:00 실주문 4건이 나갔고 KIS가 전부 거부
  ("모의투자 영업일이 아닙니다"). 무해했던 건 증권사가 막아준 덕이지 설계가 아니다.
  **진짜 위험은 15:20 시뮬 전략** — 거부해 줄 상대가 없고 KIS 시세는 휴장일에도 전 세션
  가격을 `halted=False`로 답한다(실측 005930 → 274,500). 그대로면 8개 곡선 전부에
  "열리지도 않은 날"이 박힌다.
  근본 원인: `_next_trading_day`가 보는 qlib 캘린더는 **이미 존재하는 봉으로 만들어져
  미래 날짜가 없다** → 항상 "다음 평일" 폴백. 대응: `services/trading_calendar` +
  `@market_day_only` 데코레이터(26개 태스크). **fail-open 설계** — 캘린더를 못 읽으면
  평소대로 실행한다.
- **[2026-08-17] KIS 국내휴장일조회(CTCA0903R)는 실전 전용 TR.** 모의투자에서 호출하면
  HTTP 500 `"모의투자 TR 이 아닙니다"`. 그래서 paper 환경에서는 휴장 판정이 불가하고,
  대신 **증권사 거부 응답("영업일이 아닙니다")을 redis 마커로 기록**해 이후 태스크가
  참조한다. 09:00에 기록되므로 15:20 시뮬이 그걸 보고 건너뛴다.
  판정 필드는 영업일(`bzdy_yn`)·결제일이 아니라 **개장일(`opnd_yn`)** — KIS 문서가
  "주문 가능 여부는 opnd_yn"이라고 명시. 호출은 **1일 1회 권고**라 월 단위 캐시 필수.

- **[2026-08-18] 휴장일 다음 개장일에 거래가 통째로 빠졌다 — 정적 휴장일 목록 도입.**
  08-14(금) 16:20 신호는 정상 생성됐으나 `as_of=2026-08-17`(광복절 대체공휴일)로 라벨링됐다.
  `_next_trading_day`가 보는 소스가 셋인데 모의투자에서는 전부 미래를 모른다 —
  CTCA0903R은 **실전 전용**, qlib 캘린더는 **과거 봉으로 만들어져 미래가 없음**, 남은 건
  "다음 평일" 폴백. 거부 응답 마커는 **사후에만** 동작해 금요일 시점엔 알 수가 없다.
  결과: 월요일 주문은 거부, 화요일은 `as_of=08-18` 신호가 없어 **no_signal로 주문 0건**.
  금요일 분석이 멀쩡히 살아 있는데 날짜 라벨 하나로 세션 하나를 통째로 잃었다.
  대응: `trading_calendar.KRX_HOLIDAYS` 연도별 정적 목록.
  판정 우선순위 = **거부 마커(사실) > CTCA0903R > 정적 목록 > None(fail-open)**.
  **연 1회 갱신 대상** — 연도 키가 없으면 None을 반환해 fail-open이므로 갱신을 잊으면
  그 해에는 이 방어가 없다. `12-31`은 공휴일이 아니라 **거래소 연말 폐장일**이라
  공휴일 목록만 보면 빠뜨린다. 틀렸을 때 방향성: 누락은 무해(주문 거부될 뿐),
  **개장일을 잘못 넣으면 멀쩡한 거래일을 건너뛴다** — 확신하는 날짜만 넣을 것.

### 곡선 해석에 영향을 주는 변경 (꺾임 지점)

- **[2026-08-18] 매도 대상 선정이 순위 기준으로 바뀌었다.** 그전까지
  `to_sell_codes = [c for c in held_codes ...][:n_drop]`인데 `held_codes`가 **set**이라
  순회 순서에 업무적 의미가 없었다. 보유 4종목이 전부 top-K에서 이탈했을 때 어느 2개를
  파는지가 해시 순서로 정해졌다 — 실증: 같은 조건에 08-17 실행은 `088350/010950`,
  하루 뒤 계산은 `010950/042700`. 이제 **당일 순위가 나쁜 것부터**(30위권 밖이 최하위,
  동순위는 종목코드 순) 매도한다. TopkDropout 원래 의미에 부합하고 재현 가능해졌다.
  **영향 범위는 open/close/flow 계열** — 브래킷 전략은 `to_sell_codes`가 빈 리스트라 무관.

- **[2026-08-14] 수수료·거래세 반영 시작.** 그전까지 모든 Fill이 `fee=0.0`이라 시뮬 8곡선이
  체계적으로 낙관 편향돼 있었다. `trade_cost()`(수수료 0.014% 양방향 + 거래세 0.18% 매도)를
  신설해 `Fill.fee`·`Fill.pnl`·`_simulated_balance` 현금 재구성에 반영.
  **과거 Fill은 fee=0으로 남아 있으므로 소급 재작성은 없다 — 이 날짜 이후만 비용이 붙는다.**
  되돌리려면 `live_fee_rate`/`live_tax_rate`를 0으로.
- **[2026-08-16] `limit` 진입에 `_is_risky` 적용.** 그전까지 `limit`은 거래정지·관리종목·
  투자경고 필터 없이 진입했다(open 계열에만 있었음). 이 날짜부터 위험 종목은 스킵되고
  다음 랭크가 슬롯을 가져간다 → **진입 종목 구성이 바뀌므로 곡선이 꺾인다.**
  **주의: `_is_risky`는 `client.is_mock`이면 무조건 통과**하므로 모의계좌 시뮬에서는
  이 필터가 발동하지 않는다. 즉 시뮬 곡선은 여전히 필터 없는 상태이고,
  **실계좌 전환 시에만 진입 종목이 달라진다** — 시뮬 vs 실주문 A/B 해석 시 반드시 감안할 것.
  결과 dict의 `skipped_risky`로 발동 내역을 확인.
